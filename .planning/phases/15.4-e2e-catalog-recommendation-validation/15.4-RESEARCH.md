## Summary

Esta fase adiciona dois spec files Playwright que funcionam como smoke tests de pipeline end-to-end. O objetivo não é testar UI em detalhe, mas validar que dados reais de scraping estão no banco e fluem corretamente até a IA de recomendação. Nenhuma funcionalidade nova é adicionada — apenas validação do que existe.

A infraestrutura Playwright já está completamente operacional: `playwright.config.ts` com suporte a `BASE_URL`, padrão de request API via `{ request }` fixture estabelecido em `sliceinsights.spec.ts`, e padrão de Docker local confirmado em `battle-bar.spec.ts`. Os dois novos specs devem seguir rigorosamente esses padrões existentes.

O ponto crítico de atenção: o endpoint de recomendação na UI usa `/api/v1/recommend` (sem "ations"), mas `lib/api.ts` tem `getRecommendations()` apontando para `/api/v1/recommendations` (com "ations"). Os testes Playwright devem bater no mesmo endpoint que a UI usa — `/api/v1/recommend` — conforme confirmado em `recommend/page.tsx`.

**Primary recommendation:** Criar dois specs minimalistas orientados a contrato de API, usando o fixture `{ request }` para testes de ingestão e uma sequência UI simplificada para confirmar que a IA retorna recomendações com dados reais.

### Pattern 1: API contract test com `{ request }` fixture
**What:** Testa endpoints diretamente sem browser, mais rápido e determinístico
**When to use:** Todos os testes de ingestão de catálogo (E2E-01) e testes de recomendação por API (E2E-02 direto)
**Example:**
```typescript
// Fonte: padrão estabelecido em frontend/e2e/sliceinsights.spec.ts
const API = process.env.API_URL || 'http://localhost:8002/api/v1';

test.describe('Catalog Ingestion (E2E-01)', () => {
    test('catalog/paddles has ≥10 brazil paddles with store_url', async ({ request }) => {
        const r = await request.get(`${API}/catalog/paddles?available_in_brazil=true&limit=50`);
        expect(r.status()).toBe(200);
        const body = await r.json();
        const paddles = body.data;
        expect(paddles.length).toBeGreaterThanOrEqual(10);
        for (const p of paddles) {
            expect(p.available_in_brazil).toBe(true);
            // CAT-06: store_url via market_offers
            const hasStoreUrl = p.market_offers?.some(
                (o: any) => o.store_url && o.store_url.length > 0
            );
            expect(hasStoreUrl).toBe(true);
        }
    });
});
```

### Pattern 2: Contagem de campos parcialmente preenchidos (D-02)
**What:** Valida que ≥50% das raquetes têm core_thickness ou surface_material não-nulo
**When to use:** Validação de completude de ingestão de specs
**Example:**
```typescript
// Verificação de D-02: completude de specs
const withSpecs = paddles.filter(
    (p: any) =>
        p.specs?.core_thickness_mm != null ||
        p.specs?.surface_material != null
);
expect(withSpecs.length).toBeGreaterThanOrEqual(Math.ceil(paddles.length * 0.5));
```

### Pattern 3: UI quiz flow mínimo para recomendação
**What:** Navega até /recommend, completa 3 steps do wizard, aguarda resultado
**When to use:** Validação E2E-02 via fluxo UI
**Example:**
```typescript
// Fonte: padrão de page.goto estabelecido em sliceinsights.spec.ts
test('quiz flow produces ≥1 recommendation', async ({ page }) => {
    await page.goto('/recommend');
    await page.waitForLoadState('networkidle');

    // Step 0: skill + play_style
    await page.locator('button', { hasText: 'Iniciante' }).click();
    await page.locator('button', { hasText: 'Controle' }).click();
    await page.getByRole('button', { name: /proximo/i }).click();

    // Step 1: budget — clicar em "Sem limite"
    await page.locator('button', { hasText: /Sem limite/i }).click();
    await page.getByRole('button', { name: /proximo/i }).click();

    // Step 2: submit
    await page.getByRole('button', { name: /Ver Recomendacoes/i }).click();

    // Aguardar resultado (LLM pode demorar)
    await page.waitForSelector('[class*="rounded-xl"]', { timeout: 30000 });
});
```

### Pattern 4: Validação de paddle_id cruzando catálogo (D-08)
**What:** Busca paddle_id de uma recomendação e verifica que existe no endpoint de catálogo
**When to use:** Teste de integridade referencial entre recomendação e catálogo
**Example:**
```typescript
// D-08: paddle recomendado existe no catálogo
const recResponse = await request.post(`${API}/recommend`, { data: payload });
const recBody = await recResponse.json();
const firstPaddleId = recBody.recommendations[0].paddle_id;

// Verificar via catalog
const catalogResponse = await request.get(`${API}/catalog/paddles?available_in_brazil=true&limit=100`);
const catalogBody = await catalogResponse.json();
const exists = catalogBody.data.some((p: any) => p.id === firstPaddleId);
expect(exists).toBe(true);
```

### Pattern 5: npm scripts por ambiente (D-11)
**What:** Scripts que passam env vars diferentes para direcionar para Docker local ou Vercel prod
**When to use:** Diferenciação de ambiente sem alterar playwright.config.ts
**Example:**
```json
{
  "test:e2e:local": "BASE_URL=http://localhost:3002 API_URL=http://localhost:8002/api/v1 playwright test",
  "test:e2e:prod": "BASE_URL=https://sliceinsights.vercel.app API_URL=https://sliceinsights-4rmf.onrender.com/api/v1 playwright test"
}
```

### Anti-Patterns to Avoid
- **Modificar `sliceinsights.spec.ts`:** viola D-16 e pode quebrar testes existentes
- **Adicionar `webServer` ao config:** viola D-13, o Docker externo já está rodando
- **Usar mocks:** todos os testes devem bater no backend real — a proposta é validar dados reais de ingestão
- **Hardcodar URLs nos specs:** usar sempre a const `API` com fallback para Docker local
- **Chamar `/api/v1/recommendations`:** o endpoint real é `/api/v1/recommend` (sem "ations") — confirmado no `recommend/page.tsx`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Timeout em chamadas LLM | Loop de polling manual | `page.waitForSelector(..., { timeout: 30000 })` do Playwright | Built-in com retry automático |

| Retry em CI | Lógica própria | `retries: process.env.CI ? 2 : 0` já no config | Já configurado |

**Key insight:** O projeto já tem toda a infra Playwright configurada. A tarefa é escrever os specs dentro do padrão existente, não reconfigurar a infra.

## Common Pitfalls

### Pitfall 1: Endpoint /recommend vs /recommendations
**What goes wrong:** Teste chama `/api/v1/recommendations` mas o endpoint real é `/api/v1/recommend`
**Why it happens:** `lib/api.ts` tem `getRecommendations()` apontando para `/recommendations`, mas `recommend/page.tsx` usa `fetch(\`\${apiBase}/recommend\`, ...)` — os dois coexistem e podem ser diferentes rotas
**How to avoid:** Usar `/api/v1/recommend` nos specs de E2E-02 (mesmo endpoint que a UI usa)
**Warning signs:** Teste retorna 404 ou 422 ao chamar o endpoint

### Pitfall 2: Campos de specs no response de /catalog/paddles
**What goes wrong:** Código assume `p.core_thickness_mm` mas o response aninha specs em `p.specs.core_thickness_mm`
**Why it happens:** O shape real do response usa `specs` como subobjeto (confirmado em `test_catalog_api.py` e `lib/api.ts`)
**How to avoid:** Acessar via `p.specs?.core_thickness_mm` e `p.specs?.surface_material` (campo pode ser `face_material` ou `surface_material`)
**Warning signs:** D-02 sempre falha mesmo com dados ingeridos

### Pitfall 3: Timeout insuficiente para chamada LLM
**What goes wrong:** Teste de UI falha com timeout antes da IA responder
**Why it happens:** Chamadas ao LLM (Grok) podem levar 10-20 segundos, especialmente com cold start
**How to avoid:** Usar `timeout: 30000` para `waitForSelector` na etapa de resultado; o config já tem `retries: 2` em CI
**Warning signs:** Flaky test que passa localmente mas falha em CI

### Pitfall 4: `available_in_brazil` não filtrado por padrão
**What goes wrong:** Teste conta total de paddles mas inclui os sem oferta ativa no Brasil
**Why it happens:** `/api/v1/catalog/paddles` usa INNER JOIN em offers — paddles sem offer ativo não aparecem, mas `available_in_brazil` pode não ser filtrado automaticamente
**How to avoid:** Passar `?available_in_brazil=true` explicitamente na query, e também buscar com `limit=50` para garantir amostra suficiente para o threshold de ≥10
**Warning signs:** Teste conta 0 paddles quando há dados no DB

### Pitfall 5: `store_url` em market_offers vs campo direto
**What goes wrong:** Teste procura `p.store_url` no nível do paddle mas o campo está em `p.market_offers[].store_url`
**Why it happens:** CAT-06 garante store_url por oferta, não por paddle — o shape tem `market_offers` como array
**How to avoid:** Validar com `p.market_offers?.some(o => o.store_url && o.store_url.length > 0)`
**Warning signs:** Asserção de store_url sempre falha mesmo com dados

### Pitfall 6: match_reasons vs justification/reason
**What goes wrong:** CONTEXT.md D-07 menciona `justification` ou `reason`, mas o tipo real usa `match_reasons[]`
**Why it happens:** O tipo `PaddleRecommendation` em `types/recommend.ts` define `match_reasons: string[]`, não campos individuais de justificativa
**How to avoid:** Validar via `rec.match_reasons.length >= 1 && rec.match_reasons[0].length >= 10`
**Warning signs:** Teste não consegue encontrar campo `justification` — usar `match_reasons`
