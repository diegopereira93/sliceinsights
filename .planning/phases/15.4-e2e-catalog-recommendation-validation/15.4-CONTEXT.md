# Phase 15.4: Validação E2E do Catálogo e Recomendação com Playwright - Context

**Gathered:** 2026-03-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Garantir com testes Playwright que raquetes ingeridas estão disponíveis no catálogo e funcionam no fluxo de recomendação IA — validando a integridade da pipeline de ingestão de ponta a ponta. Não adiciona funcionalidade nova; apenas valida o que já foi construído nas fases 11–15.

</domain>

<decisions>
## Implementation Decisions

### Critério de ingestão válida (E2E-01)
- **D-01:** `GET /api/v1/catalog/paddles` deve retornar ≥10 raquetes com `available_in_brazil=true` e `store_url` não nulo
- **D-02:** Pelo menos 50% das raquetes retornadas devem ter `core_thickness` ou `surface_material` preenchidos (não null)
- **D-03:** `GET /api/v1/catalog/stores` deve retornar ≥1 loja com `name` e `base_url` preenchidos
- **D-04:** A contagem mínima de 10 raquetes garante que não é apenas dado de seed local — valida ingestão real dos scrapers

### Profundidade do teste de recomendação IA (E2E-02)
- **D-05:** Quiz completo via UI → resposta da IA deve incluir ≥1 recomendação (não array vazio)
- **D-06:** Cada recomendação deve ter `store_url` real (não null, não string vazia, não placeholder)
- **D-07:** Cada recomendação deve ter campo `justification` ou `reason` com texto não vazio (≥10 chars)
- **D-08:** O paddle recomendado deve existir no catálogo — `paddle_id` retornado deve bater com um registro em `/api/v1/catalog/paddles`
- **D-09:** Usar a API diretamente (`POST /api/v1/recommendations`) além do fluxo UI para teste mais rápido e determinístico

### Ambiente de execução (E2E-03)
- **D-10:** Dois ambientes via env var: Docker local (`BASE_URL=http://localhost:3002`, `API_URL=http://localhost:8002/api/v1`) e produção Vercel
- **D-11:** Adicionar scripts npm no `package.json` do frontend: `test:e2e:local` e `test:e2e:prod`
- **D-12:** Manter compatibilidade com `playwright.config.ts` existente — `BASE_URL` env var já suportado
- **D-13:** Seguir padrão atual: sem webServer no config (Docker externo já rodando)

### Organização dos spec files
- **D-14:** Criar `frontend/e2e/catalog-ingestion.spec.ts` — valida ingestão (D-01 a D-04)
- **D-15:** Criar `frontend/e2e/recommendation-e2e.spec.ts` — valida fluxo de recomendação IA (D-05 a D-09)
- **D-16:** Não modificar `sliceinsights.spec.ts` — manter testes existentes intactos

### Claude's Discretion
- Número exato de retries e timeouts dentro dos specs
- Seleção de quais respostas de quiz usar para o teste de recomendação (qualquer combinação válida)
- Formato exato dos npm scripts (prefix, flags)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `playwright.config.ts`: já tem `BASE_URL` env var configurado — usar sem modificar
- `sliceinsights.spec.ts` `API` const: padrão `process.env.API_URL || 'http://localhost:8002/api/v1'` — reusar nos novos specs
- `sliceinsights.spec.ts` `test.describe('API Contract')`: estrutura de request direto à API — seguir para catalog/recommendation tests

### Established Patterns
- Testes de API usam `{ request }` fixture do Playwright (não `page.goto`) — mais rápido e determinístico
- Testes de UI usam `page.waitForLoadState('networkidle')` antes de asserções
- Sem mocks — todos os testes batem no backend real (Docker ou Vercel)

### Integration Points
- Docker: frontend na porta 3002, API na porta 8002 (confirmado pelo battle-bar.spec.ts e playwright.config.ts)
- `package.json` do frontend precisa de novos scripts `test:e2e:local` e `test:e2e:prod`

</code_context>
